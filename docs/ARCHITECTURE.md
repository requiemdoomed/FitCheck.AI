# FitCheck.AI architecture

_Author: Swayam Shakya_

## Overview

One origin, three parts:

1. **Browser.** The HTML pages and ES modules in `assets/js`. Pages call `api.js`, a small
   `fetch` client that sends cookies and the CSRF header. Some work stays in the browser
   because it's interactive or saves server time:
   - garment cut-outs: U²-Net-p on onnxruntime-web, `local/images.js`;
   - the colour hint and pattern detection;
   - Smart buys: `engine/shop.js`;
   - the weather lookup: `local/weather.js`, Open-Meteo.
2. **Flask server** (`backend/`), behind gunicorn:

| module | role |
|---|---|
| `app.py` | app factory; CSRF check before requests; cookies and security headers after; JSON errors; static whitelist (pages and `assets/` only) |
| `security.py` | scrypt passwords, server sessions (token hash in MySQL, idle and absolute expiry), CSRF/Origin, rate limits, Fernet sealing of keys |
| `api_auth.py` | register, login, logout, logout-all, me |
| `api_wardrobe.py` | items CRUD, uploads (Pillow validation and re-encoding), owner-only image serving |
| `api_outfits.py` | generate (Python engine), history, feedback, save, wear, dashboard |
| `api_photos.py` | photo settings and keys, outfit photos (4 takes), Smart buys photos, cached public samples |
| `api_profile.py` | profile, preferences, password, export/import, delete, demo wardrobe |
| `photo_engine.py` | prompt writing, clothing-photo board, Pollinations (model discovery, text and edit models), Gemini |
| `store.py` | shared queries, JSON shapes, image storage |
| `mailer.py` | password-reset email over SMTP with TLS (background thread); logs the message in development when no SMTP is set |
| `manage.py` | operator commands: `reset-link`, `prune`, `stats` |
| `db.py`, `schema.sql`, `init_db.py` | PyMySQL connection per request, commit/rollback, schema |

3. **MySQL 8**, with these tables:
   - `users`, `sessions`, `password_resets`, `rate_events`, `preferences`, `secrets`;
   - `images` (MEDIUMBLOB), `items`, `outfits`, `outfit_items`, `outfit_photos`;
   - `feedback`, `saved_outfits`.

   Every user-owned row cascades on account deletion.

## Offline and install

`sw.js` (generated by `scripts/build_sw.py`) precaches the 74 app-shell files: pages, CSS,
JS modules, fonts and icons. It answers from the network first and falls back to the
cache, then to `offline.html`. `/api` is never cached. `manifest.webmanifest` and
`assets/images/icons/` make the site installable. The server serves both from the root,
and `sw.js` with `no-cache`.

## A request

1. The browser sends `POST /api/recommendations/generate` with the `fc_session` cookie and
   an `X-CSRF-Token` header.
2. `check_csrf`: the header matches the `fc_csrf` cookie, and the Origin is the site.
3. `login_required` hashes the token, finds a live session, and checks its idle and
   absolute limits.
4. The handler validates the input (`validation.V`), loads the user's active items and
   their recent wears, and runs `fitcheck_ml.recommender` with the joblib models. It stores
   the outfit and returns JSON.
5. `after_request` adds cookies (on sign-in), CSP and the other headers, plus `no-store`.

## Photos

`POST /api/photos/outfit/<id>` writes a catalogue-style prompt from the pieces (colour,
type, fabric, pattern) and the person's preferences, then calls the chosen engine:

| engine | how it makes the photo |
|---|---|
| free, no key | Pollinations FLUX.1 text-to-image |
| free, with key | discovers models: Z-Image for text; FLUX.2 klein / Qwen-Image / Kontext edit a board of the actual clothing photos |
| Gemini, user's key | best image model on the key, with the clothing photos as references |

The result is checked to be a real image, stored in `images`, and served from
`/api/images/<key>`. An outfit keeps four takes.

## Why the engine moved to the server

The browser-only version needed a JavaScript port of the Python engine and exported
models. With a server, `ml/fitcheck_ml` runs as-is, so there is one engine, the same code
the notebook evaluates, and models load once per worker.
